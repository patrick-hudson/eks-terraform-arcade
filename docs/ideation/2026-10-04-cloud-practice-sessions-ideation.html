Codebase Context

The kit already has 24 live missions, seven authored simulations, guarded Terraform operations, prerequisite metadata, browser lesson stages and a separate live-result receipt verifier. The biggest opportunity is connecting these pieces into a coherent study session.

The browser currently keeps practice history locally and presents commands; the terminal directly manages a subset of environments. Most runtime verification shows state and pod observations, while richer mission checks live in another path. Cost guidance has hourly components, but mission prices remain prose. These are integration gaps with concrete learning consequences.

All durable fixes must remain in Terraform. The account has unrelated resources. The learner’s allowance is $20; developer smoke testing has a separate few-dollar bound within that overall restraint. Resource ownership, reviewed scope and deletion evidence therefore belong inside the normal workflow.

1. Guided cloud sessions

Spend and clean up · Confidence 92% · Complexity High

Choose a lesson or a short incident queue, see total and marginal1h/2h estimates, then review each prerequisite plan and track the live session until named cleanup checks succeed. Surface the same session state and actions in browser and terminal.

Basis
direct: combines P1,I1,I2,I6,L2,X5 against existing registered runtime and shared-cluster guidance.
Rationale
This turns the existing fragments into one complete provision-practice-delete experience.
Downsides
Session orchestration spans failure recovery, multi-root dependencies and resource-specific deletion evidence. Build around the existing guarded runtime; a single green session label would hide uncertainty.

2. A repair submission with evidence

Prove and retain learning · Confidence 93% · Complexity High

Submit a source repair to a mission-specific behavioral checker, compare starting and recovered evidence, then explain the decisive observation before finishing. Keep simulated answers, observed cloud checks and cleanup status visibly distinct.

Basis
direct: combines A1,A2,L3,L5 against existing playbooks, receipt verifier and bounded practice history.
Rationale
This is a defensible infrastructure analogue of a coding exercise submission.
Downsides
Behavioral checks must be authored per failure and tested on real infrastructure. External observations and a stable plan each prove only part of the contract; neither is a certificate of interview readiness.

3. One mission, two polished clients

Move between browser and terminal · Confidence 91% · Complexity High

Give web and TUI the same mission capabilities, state labels, theme semantics and contextual next action. Preserve platform-appropriate interaction rather than copying layouts pixel for character.

Basis
direct: combines L1,L6,C4,P4 against existing shared recipes but divergent runtime and learning UI.
Rationale
Polish and parity reinforce a single understandable study workflow.
Downsides
Parity can multiply implementation effort unless all clients call shared capabilities. Browser mutation changes the trust boundary and needs deliberately bounded operations and explicit saved-plan approval.

4. Same symptom, different fault

Investigate and repair · Confidence 84% · Complexity Medium

Build fault families in which the visible complaint stays constant while the defective Terraform input varies. Assign one authored variant per attempt and require a fresh evidence path.

Basis
direct: practice/cases.json already pairs Service and pending-Pod symptoms with different causes.
Rationale
It discourages memorizing the fix associated with a mission title.
Downsides
Every variant adds fixture and acceptance maintenance. Start with a few valuable AWS/Kubernetes fault families instead of adding dozens of unverified challenges.

5. Show symptoms before services

Choose and resume practice · Confidence 82% · Complexity Low

Let learners choose missions by observed symptom, available time and skill rather than numbered service names alone. Keep service filters available for targeted study.

Basis
direct: docs/learning-design.md:5 says record the first observed failure before editing.
Rationale
It matches an interview where the candidate receives a complaint rather than the root cause.
Downsides
Filters can accidentally reveal the diagnosis. Use neutral complaints, distinguish practice duration from provision/delete time, and preserve direct mission navigation.

Recommended next direction: the cloud session loop

Develop Guided cloud sessions with Repair submission and One mission, two polished clients as its supporting capabilities. The learner should see prerequisite readiness, the exact next action, estimated one- and two-hour cost, the actual checked scope and outstanding cleanup in either client.

Prove the loop on the low-cost Lambda/DynamoDB fault and a short EKS session spanning a pod failure and a real traffic check. Expand multi-root missions through explicit dependency stages. Preserve the same source files, state ownership and reviewed-plan safeguards rather than building a second execution system.

Keep new fault families and symptom-led discovery as follow-on directions once a repaired and deleted cloud session is demonstrably reliable. More lesson count is less valuable than a small set whose initial failures, durable repairs and teardown have been observed.

Design implications

  • Show one contextual next action, with advanced operations still easy to find. Keep the environment, working directory and billable status visible.
  • Make navigation easy to recognize while diagnosis requires the learner to recall, predict and explain. Do not reveal the defective field in a challenge title.
  • Use purple for selection and primary actions. Success, failure, unknown and cleanup-needed states need words and distinct semantic treatments.
  • Respect system dark mode with a persistent explicit choice. Inspect dialogs, code blocks, keyboard focus and muted labels in both themes.
  • Keep billable environment time separate from an unfinished learning attempt. Reflection can continue after deletion using saved observations.
  • Parity means the same supported actions, evidence and vocabulary. A terminal should remain keyboard-first rather than imitate browser cards.
